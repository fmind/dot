# Workstation Authentication

The [README](https://github.com/fmind/dot#authentication--logins) lists the login commands and `dot login --help` their options; this guide owns their policy.

- **Fixed order**: a bare `dot login` reconciles the `auth.login` providers (default `[github, gcp, workspace]`; add `colab` where it is used) in a fixed order whatever the list order: `setup github`, GCP and ADC (Workspace setup lists and enables APIs through gcloud, and Colab shares ADC), Workspace setup (only when `GWS_PROJECT` or `auth.workspace.project` names a project), Workspace login, then Colab, skipping ready steps and stopping on failure. Set `auth.login` per machine in its unmanaged config, since credential lifetimes follow each account's session policy.
- **Probe before any browser**: every distinct readiness probe runs concurrently first, and each invocation reuses a result in memory until a login or setup command changes provider state; a login skips only when usable credentials cover the requested scopes. `dot login --check` covers the `auth.login` providers, GitHub including removed grants, so agents can ask before starting a browser flow. Options go before no provider (`dot login --check`) or after one (`dot login gcp --check`).
- **Fail closed**: unknown status fails with recovery guidance instead of starting authentication; repair or remove environment-token overrides that prevent OAuth updates. Failed probes print no captured tokens or provider payloads, and Dot persists no credential cache.
- **Interactive steps**: GitHub login uses the web flow with gh's configured `git_protocol`, leaving only gh's SSH-key choice and its Enter-to-open prompt. gws only prints its OAuth URL, so dot opens it through `$BROWSER` (or `open` on macOS); over SSH or without a display, open the printed URL yourself.
- **GCP**: CLI and ADC credentials are checked separately without asserting one identity, and only the missing one re-authenticates: `gcloud auth login` for the CLI, `gcloud auth application-default login --scopes=<auth.gcp.adc_scopes>` for ADC. Requesting a token for the configured scopes proves the ADC grant, because Google rejects scopes outside it.
- **Workspace setup**: reads enabled APIs from `gws auth status` for its configured project (falling back to `gcloud services list` for another project), enables only missing configured APIs, and skips OAuth client setup when the project already has a readable client configuration.

For a read-only cross-provider sweep of login state, expiry, scope gaps, and re-login commands (including Hugging Face, Kaggle, AWS, Databricks, and Atlassian), use [auth-status](../../auth-status/SKILL.md); this guide owns the login policy it reports against.

Workspace project selection uses the setup argument, then `GWS_PROJECT`, then `auth.workspace.project`. GitHub login always targets github.com. Inspect policy with `dot config show` and edit it with `dot config edit`: `auth.github.scopes`, `auth.github.remove_scopes`, `auth.workspace.scopes`, `auth.workspace.apis`, `auth.gcp.adc_scopes`, and `auth.login`. Maps merge with defaults; configured lists replace the entire default list.

**Workspace scope limit:** Google's consent page hangs after Allow when one login requests more than 50 scopes (logins of 45, 47 and 50 completed; 52 and more hung, bisected 2026-10-26). One-off grants share that consent, so the 48 defaults leave two one-off slots, and `dot login workspace` refuses a request above 50 before opening a browser. The default policy holds the everyday user-level writes and only the read-only scopes a consumer narrows its token to, because a write scope already allows reads. GitHub adds Projects, profile, and organization audit-log reads to repository, workflow, gist and notification access; GitHub drops a read scope implied by a granted write itself. Workspace writes cover Gmail (`gmail.modify`, basic settings), Drive, Docs, Sheets, Slides, Forms, Calendar, Contacts, Chat messages and spaces, Tasks, Apps Script projects, Analytics (`analytics.edit`, `analytics.manage.users`), Search Console (`webmasters`) and Business Profile. The read-only scopes are those the brain's sensors and google CLI narrow their tokens to: Gmail, Postmaster Tools, Drive, Docs, Calendar, Contacts, Tasks, Chat, Meet, Forms responses, Analytics, Search Console, YouTube and YouTube Analytics, Admin Directory, audit and usage reports, and Chrome policies and reports. gws replaces its whole grant on login, so a custom `auth.workspace.scopes` list must keep them. A new Workspace API also needs `dot setup workspace` to enable it in the OAuth project.

**One-off grants:** write access beyond the policy serves one task, then goes. When a command fails for a missing scope, ask the user to run the exact `--grant` command below, finish the task, then ask them to run the revert command. `dot login workspace --grant SCOPE` (a URL, or a short name such as `admin.directory.user.security`) adds a scope to one login; a later `dot login workspace` reports the extra scopes, and `dot login workspace --force` returns to the configured grant, so gws forgets the wider refresh token and its cached access tokens. `dot login github --grant SCOPE` adds one; `dot setup github` (or a bare `dot login`) removes every `auth.github.remove_scopes` entry afterwards, and for a scope outside that list the login prints its removal command. gh's minimum scopes `repo`, `read:org` and `gist` cannot be removed, so the policy keeps them.

Possible one-off grants, by product (source: [GitHub scopes](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps), [Google scopes](https://developers.google.com/identity/protocols/oauth2/scopes)):

- **GitHub keys**: `write:public_key`, `write:ssh_signing_key`, `write:gpg_key` (and their `admin:` forms) to add a machine key; a stolen token could otherwise plant persistent access.
- **GitHub packages and organizations**: `write:packages` for a manual image push, `delete:packages`, `delete_repo`, `write:org`, `admin:org` (organization security settings, then remove it at once), `admin:org_hook`, and `codespace` (billable).
- **Admin Directory writes**: `admin.directory.user`, `.user.alias`, `.user.security` (tokens and app passwords), `.group`, `.group.member`, `.orgunit`, `.domain`, `.customer`, `.rolemanagement`, `.resource.calendar`, `.userschema`, `.device.chromeos`, `.device.mobile`, `.device.mobile.action`, `admin.chrome.printers`, `admin.datatransfer`, `apps.licensing`, `apps.groups.settings`.
- **Other administration**: `chrome.management.policy`, `chrome.management.profiles`, `chat.admin.spaces`, `chat.admin.memberships`, `chat.admin.delete`, `cloud-identity.groups`, `cloud-identity.policies`, `cloud-identity.inboundsso`, `drive.admin.labels`, `ediscovery` (Vault holds and exports).
- **Public or destructive user actions**: `tagmanager.publish`, `tagmanager.delete.containers`, `tagmanager.manage.users`, `tagmanager.manage.accounts`, `analytics.provision`, `analytics.user.deletion`, `chat.delete`, `postmaster`, `postmaster.domain`, `postmaster.user`.
- **Extra reads**: `drive.activity.readonly`, `drive.labels`, `drive.admin.labels.readonly`, `chat.admin.spaces.readonly`, `chat.admin.memberships.readonly`, `chrome.management.{appdetails,profiles,telemetry}.readonly`, `admin.directory.{group.member,user.alias,userschema,resource.calendar}.readonly`, `admin.datatransfer.readonly`, `admin.chrome.printers.readonly`, `cloud-identity.{groups,policies,inboundsso}.readonly`, `ediscovery.readonly` (Vault), `yt-analytics-monetary.readonly`, `script.metrics`, `meetings.conference.media.readonly` (Meet Media API preview).
- **Extra user writes**: `chat.memberships`, `chat.users.readstate`, `meetings.space.created`, `meetings.space.settings`, `script.deployments`, `script.processes`, `cloudsupport`, `directory.readonly` (organization directory), `userinfo.profile`, `tagmanager.readonly`, `tagmanager.edit.containers`, `siteverification`, `chat.customemojis`, `chat.users.sections`, `chat.users.spacesettings`.
- **Personal profile data and Keep**: `user.phonenumbers.read`, `user.addresses.read`, `user.birthday.read` and the other `user.*.read` People scopes; `keep`, `keep.readonly` (Keep API availability depends on the Workspace edition; untested).

Refused, never granted:

- **GitHub**: enterprise scopes (`admin:enterprise`, `manage_runners:enterprise`, `manage_billing:enterprise`).
- **Gmail**: `https://mail.google.com/` (immediate permanent deletion) and `gmail.settings.sharing` (forwarding and delegates, a silent exfiltration path).
- **Through gws**: `cloud-platform`, because GCP access belongs to gcloud and IAM.
- **YouTube writes through gws**: `youtube`, `youtube.upload`, `youtube.force-ssl` do nothing there, because the @fmind-dev channel belongs to a Brand Account outside the organization that the gws OAuth client is limited to; the brain's `google.py youtube URL --write` uses the channel owner's own `youtube.force-ssl` grant instead.
- **Not applicable**: `apps.alerts` (Google rejects it as `invalid_scope` for user logins; Alert Center documents only service accounts with domain-wide delegation), `chat.app.*` and `chat.import` (Chat app and import identities), `youtubepartner*` (YouTube CMS partners), and Classroom scopes (no Classroom use).

Gmail uses `gmail.modify`, which excludes immediate permanent message deletion; full Drive and other editing scopes can still permit destructive operations. Per-machine signing keys follow the [commit signing](https://github.com/fmind/dot#commit-signing) setup. OAuth capability does not authorize deletion or contacting others, including opening Cloud Support cases. GCP permissions remain controlled by IAM. Applying configuration does not change issued tokens: authenticate again for new scopes and use `dot setup github` to remove excluded grants. Personal Google accounts need a Workspace policy without `directory.readonly`. `dot login github`, `dot setup github`, and `dot doctor --deep` warn when gh stored the token in plaintext `hosts.yml` because no keyring accepted it; unlock the system keyring, run `gh auth logout`, then `dot setup github`. gh prints its one-time code instead of copying it (`clipboard: disabled` in `~/.config/gh/config.yml`), because `wl-copy` never returns under ChromeOS Crostini's Sommelier and gh would hang before showing the code. Workspace login on Crostini prints a reminder: gws redirects to `http://localhost:PORT` but listens on `127.0.0.1` only, and ChromeOS forwards only the IPv4 address, so a tab that hangs after Allow resumes once `localhost` becomes `127.0.0.1` in its address.

## Colab ADC

ADC replaces its whole grant on every login, so `auth.gcp.adc_scopes` owns every ADC consumer's scope: gcloud's defaults (`openid`, `userinfo.email`, `cloud-platform`, `sqlservice.login`) plus `colaboratory` and the read-only scopes the brain's sensors narrow their tokens to (`bigquery.readonly`, `logging.read`, `cloud-platform.read-only`). `dot login gcp` and `dot login colab` request the same list, so neither drops the other's scopes. `dot login colab` refuses a list without the Colab scopes, then authorizes only when the scoped ADC refresh fails (or with `--force`) and verifies session access:

```bash
gcloud auth application-default print-access-token --scopes=<auth.gcp.adc_scopes> >/dev/null  # readiness; never print the token
gcloud auth application-default login --scopes=<auth.gcp.adc_scopes>               # only when needed
colab --auth=adc sessions
```

A 45-second timeout bounds both checks. Session access alone does not prove the full scope grant, so the scoped refresh decides whether to skip authorization. `--dry-run` prints the login and session commands without probing. Session inspection allocates no VM. An empty listing is accepted only without authentication failure diagnostics, since Colab can exit successfully after an ADC failure. Unknown failures require native inspection before retrying.

Colab uses the shared ADC file, so this login replaces its existing user credentials and scope grant without changing the gcloud CLI account. `GOOGLE_APPLICATION_CREDENTIALS` takes precedence; repair or unset it before changing stored ADC. If a native login replaces ADC without the Colab scope (such as `gcloud auth login --update-adc`), run `dot login colab` again.

## Customer overrides and isolation

**Customer accounts:** Hugging Face's nonempty `HF_TOKEN` overrides its token file; set `HF_TOKEN_PATH` before starting Python when selecting a separate file. Kaggle's personal access-token file takes precedence over legacy keys and OAuth; `KAGGLE_CONFIG_DIR` does **not** redirect it. Select `KAGGLE_API_TOKEN` explicitly for customer work. OpenCode's saved login can override an environment key; use project `provider.openrouter.options.apiKey` with an environment/file reference, or isolate its login with `XDG_DATA_HOME`. Empty environment variables are not a universal way to disable native credentials. See the [HF environment reference](https://huggingface.co/docs/huggingface_hub/en/package_reference/environment_variables), [Kaggle token resolver](https://github.com/Kaggle/kaggle-sdk-python/blob/main/kagglesdk/kaggle_env.py), and [OpenCode providers](https://opencode.ai/docs/providers/).

Kaggle 2.2 tries legacy keys and OAuth if an access token is invalid; the scoped helper does not change native authentication behavior. For strict customer separation, use a separate OS account/container or a dedicated home and credential configuration without personal logins. A missing customer HF token file yields no saved token, but may permit anonymous operations; it does not guarantee an authentication error for public resources.

## Scoped credentials

`dot secret run NAME -- COMMAND ...` uses an existing `NAME` environment value first, then `~/.config/dot/secrets/NAME`. An explicitly empty value, missing/insecure file, or malformed credential fails before the command starts. It never retries with personal credentials after an authentication failure. This helper is an explicit opt-in to personal credentials: use the ordinary command for customer profiles and ADC. Child processes inherit the selected key and the rest of the existing environment; the parent shell does not gain the key. This is credential scoping, not a sandbox or an environment scrubber. Arguments, terminal input/output, and exit status are preserved. Nest the helper if a command needs multiple keys. Shell startup exports no API keys; native HF, Kaggle, and OpenCode logins are seeded only when absent. See [secret setup and migration](https://github.com/fmind/dot#secret-management).

The only managed scoped key is `OPENROUTER_MANAGEMENT_KEY` (read-only OpenRouter usage reporting). No personal Google, Gemini, Antigravity SDK, or Stitch key is stored: Google model access uses ADC ([GCP Agent Platform](../../model-providers/references/gcp-agent-platform.md)), and apply deletes the retired `ANTIGRAVITY_SDK_API_KEY`, `JULES_API_KEY`, `STITCH_ACCESS_TOKEN`, `UV_PUBLISH_TOKEN`, and `VERTEX_API_KEY` files. PyPI packages publish through [Trusted Publishing](https://docs.pypi.org/trusted-publishers/) in CI; `dot secret run` rejects `UV_PUBLISH_TOKEN` so no long-lived personal upload token returns. Use native `uv publish` with explicitly selected credentials for other registries.
