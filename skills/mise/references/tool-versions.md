# Tool Versions

Keep every project independently pinned and installable. [upgrade-tools](../../upgrade-tools/SKILL.md) owns upgrades; this reference owns selection for new and existing projects.

## Workstation and projects

- **The workstation config owns only the workstation**: `~/.local/share/chezmoi/dot_config/mise/config.toml` owns requests and options; the adjacent `mise.lock` owns exact resolutions. `fmind/dot` tracks `latest` by default for all tools, including Python. An intentional compatibility or release-channel exception needs a reason beside its declaration; Python has no blanket minor-version exception.
- **Lock with revision 3 bundles**: use lockfile revision 3 (mise 2026.9.16+; it also pins forge repository IDs) and keep each lockfile with its referenced native dependency files. `mise lock --upgrade` migrates an older lockfile once; mise otherwise keeps a lockfile's revision. The workstation stores these under `dot_config/mise/locks/`; `mise run lock` captures the shared graph and removes previously referenced files that mise retired. Leave generated bytes unchanged and use `--locked` installs. Preserve the pgcli `with` requirement; validate fresh installations after graph updates.
- **Projects own their pins**: other repositories under `~/fmind`, `~/fmind-ai`, and `~/mlops-courses` declare fixed mise versions with their own lockfiles and change them only during their own requested upgrade. A workstation or sibling upgrade never changes them, and neither do their application dependencies. Use only the tools each project needs. Do not import or symlink personal configuration into a project or require this checkout in its CI.
- **Separate runtime pins from `requires-python`**: pin Python like every other mise tool and align `.python-version` when present. Keep `requires-python` as the package's supported range; a newer interpreter pin does not automatically raise its minimum or drop tested interpreters.
- **Treat template `latest` as a placeholder**: `latest` in a reusable scaffold is a selection placeholder. Replace it with an exact version before installing or delivering a project; template examples are not a second version catalog.

## Select exact versions

1. **Seed new projects from installed versions**: when creating a project, prefer the workstation's locked version of each required tool so installations are reused. Read lock data with TOML tooling; do not execute the template or infer versions from `latest` or the active shell. The seed is a starting point, not a binding: the project owns the pins afterwards.
1. **Upgrade existing projects on their own request**: resolve the current stable release of the project's own tools during that project's upgrade. Do not align it with the workstation or sibling repositories; a newer project pin is never downgraded to match them.
1. **Match full installation identity**: tool, backend, install options, and target platform. Normalize equivalent aliases deliberately when they would create duplicate installations; preserve required options and verify the selected backend. Matching version strings alone does not establish identical installations.
1. **Cover every project declaration**: check root, nested, environment-specific, and task-level tool declarations that belong to the project, along with relevant CI and runtime version files. Preserve intentional test matrices and platform-specific requirements. A genuine incompatibility stays as an exact pin with a concise reason and the failed validation evidence.

Use the installed CLI's native explicit target when recording a selected version:

```bash
mise use --path mise.toml --pin <tool>@<exact-version>
mise lock
mise tasks validate
mise run all
```

`mise use` installs missing tools as well as editing configuration. Inspect diffs and resolve backend ambiguity before invoking it. If a new config is untrusted, review it and run `mise trust -y mise.toml` before retrying. Normal installations consume the recorded versions; an upgrade is an explicit operation.
